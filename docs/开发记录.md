# 本轮开发记录（2026-09-04 ～ 2026-09-05）

本轮从一次完整代码审核开始，按五个批次实施，另外补充了真机安装脚本与新的应用图标。
本文只记录做了什么、为什么这样做、以及踩过的坑；逐条构建与测试结果见
[执行日志](执行日志.md)，待办与范围边界见 [优化计划](优化计划.md)。

## 一、起点与核心需求

核心需求：**iOS 27 / iPhone 16 Pro 上的双摄拍照与录像**。

审核结论是：保存、恢复、并发这套工程骨架扎实，真正的问题在于画质与录像体验被一批
保守常量锁死在远低于硬件能力的水平。四项达成度里有三项不合格：

| 维度 | 起点 | 结束 |
| --- | --- | --- |
| 双摄拍照 | 810×1440（1.17MP，约 1MB） | **2268×4032（9.1MP，约 2.5MB）** |
| 双摄录像 | 720×1280 / H.264 3.5Mbps / 单声道 | **长边 1920 / HEVC / 采集端推荐音频** |
| 录像所见即所得 | 画中画位置硬编码，无视用户布局 | **与预览、照片共用布局引擎** |
| iOS 27 工具链 | 默认 Xcode 无法构建目标 | **已定位并固化到文档与脚本** |

## 二、五个批次

### 批次 0：解除阻塞

本机装有两个 Xcode，而 `xcode-select` 指向的恰好是**不能**构建 iOS 27 目标的那个
（26.6，仅 iOS 26.5 SDK）。可用的是 `~/Downloads/Xcode-beta.app`（27.0，iOS 27.0 SDK）。

这一条被写进 `CLAUDE.md` 正文而非仅留在环境文档里，因为后续任何会话直接照抄命令都会
撞上这个坑。同时修正了 README 与 CLAUDE.md 中已失效的模拟器测试命令（`OS=26.5` →
`OS=27.0`，本机已无该 runtime）。

建立回归基线：83 项单元测试 + 3 项 UI 测试全部通过。

### 批次 1：画质补齐

成片只有 1.17MP 是三处保守配置叠加的结果，必须一起改，单改任何一处都无效：

1. `DualCameraLayoutEngine.outputSize` 的画布长边硬编码为 1440；
2. `CameraFormatSelector` 以 1280×720 为目标，且对 1080p 以上做 6 倍惩罚；
3. `PhotoCaptureCoordinator` 从不设置 `maxPhotoDimensions`，系统只给格式的默认较小尺寸。

改法：画布长边改为按后摄源图推导；格式评分按模式拆开（照片按最大可拍照片尺寸倒序，
录像目标提到 1080p）；拍照时显式设置 output 与每次请求的尺寸上限。

**真机专属崩溃**：首版装机即闪退。

```
-[AVCapturePhotoOutput setMaxPhotoDimensions:] May not be set until connected
to a video source device with a non-nil activeFormat
```

本项目的 MultiCam 图用 `addOutputWithNoConnections` 搭建，output 在连接建立前没有视频源
设备。该异常是 NSException，Swift 侧捕获不到，写错顺序就是直接杀进程。Fake Camera 不走
真实 AVCapture 路径，模拟器测不出来——**涉及 AVFoundation 配置顺序的改动必须装机验证**。

**用户反馈引出的补充修复**：看到 2268×4032 这个实测结果后意识到，仅按源图长边推导会让
1:1 画幅上采样（3024 宽的源图被拉到 4032）。补上「源图短边 / 画幅比」约束，保证任何画幅
都不上采样，并加了跨全部画幅断言缩放系数不超过 1 的用例。

### 批次 2：录像体验

录像此前固定 720×1280，画中画位置硬编码，无论用户把小窗拖到哪、选了分屏还是改了画幅，
成片都不变。改为与预览、照片共用 `DualCameraLayoutEngine`，三种布局与三种画幅全部生效。

同时提升规格：长边 1920（9:16 为 1080×1920，3:4 为 1440×1920，1:1 为 1920×1920）、
HEVC 编码、码率按像素数缩放、音频改用采集端 `recommendedAudioSettingsForAssetWriter`。

**坐标系**：布局引擎输出 UIKit 坐标（原点左上、y 向下），视频合成走 CoreImage
（原点左下、y 向上）。新增 `coreImageRect(from:canvasHeight:)` 显式翻转。判断需要翻转的
依据来自用户的实测反馈——画中画实际固定在**左下角**，而代码字面写的是右下。

**性能**：帧回调与合成移出 `sessionQueue`，改用独立的 video-output 串行队列。此前逐帧渲染
与对焦、缩放、设备加锁、停止录制共用一条队列。CIContext 改为按 Metal 设备共享。
前摄帧与后摄帧时间差超过 0.2 秒即不参与合成，避免前摄停顿时把过期画面持续贴在成片上。

**测试拦下的回归**：实现中把 `isFinishing = false` 移出了 `sessionQueue.async`，同时破坏
两项既有不变量——收尾闸门在 `finishWriting` 返回时就打开而非等回调送达控制器；且该行移走
后 `[self]` 在块内不再有实际使用，捕获被编译器省略导致协调器提前释放。
`VideoResourceTests` 的两条用例同时捕获了这两点。

### 批次 3：起录延迟

切换拍照／录像模式、切镜头、改质量都会重建 Session，而每次重建都从零重跑成本搜索：
最多 12 轮「改格式 → 建完整图 → 提交 → 读成本 → 拆图」。这是按下录制键后黑屏等待的
主要来源。改为按「前摄设备 + 后摄设备 + 采集模式」缓存已验收组合，命中后只需 1 轮。

同时修掉「起录时缩放被重置」：此前一律 `resetZoom`，放大到 3× 按下录制会弹回 1×。
现在同一颗镜头恢复此前缩放，换镜头仍重置。

**评估后未实施**：照片与视频输出共存以实现零延迟起录。同一张 MultiCam 图上叠加两路
PhotoOutput 与两路 VideoDataOutput 加音频会抬高 `hardwareCost`，很可能把批次 1 刚验收
通过的高分辨率照片格式挤下去，即**用画质换起录速度**，方向不对。

### 批次 4：界面补齐

- **补光**：此前完全没有，夜间基本不可用。MultiCam 下照片闪光灯通常不可用，但手电筒是
  设备级属性，前后摄并发时依然能开，因此以「常亮补光」实现。重建 Session 后重新施加，
  退出界面时主动关闭。
- **曝光补偿**：右侧竖向滑杆，仅在设备报告有效范围时出现。
- **AE/AF 锁**：长按后摄画面切换，锁定时显示黄色徽标。
- **缩放读数**：此前直接显示 `videoZoomFactor`，超广角下读出 1.0× 而镜头菜单标 0.5×，
  自相矛盾。改为等效焦距倍率。上限由 6× 放开到 12×。
- **倒计时可取消**：整屏可点。
- **模式切换**：底部改为「照片／视频」切换加单一主键，取代此前快门与录制两个同屏按键
  （且录制中白快门变方块承担停止，一个控件承担两种语义）。纯界面改动，不改变会话建图时机。
- **查看页**：淡入缩放转场；照片支持双指缩放、双击切换、放大后拖动、下滑关闭。

**UI 测试拦下的布局遮挡**：模式切换器加在主键上方后与底部状态提示条重叠，提示存在时
无法点到模式切换。提示条 `padding(.bottom)` 由 126 抬到 184。这是真实遮挡，不是测试问题。

### 批次 5：工程健康度

- **`CameraNoticeCenter`**：提示的发布时序（主队列串行化、唯一 ID 消费、按媒体任务解除、
  无操作提示的自动消失）从 Controller 移出。自动消失的调度器可注入，测试无需真的等待。
- **`RecentMediaState`**：最近媒体排序与视频去留的纯状态机，不接触 AVFoundation、PhotoKit、
  文件系统与界面。
- **并发检查**：`minimal` → `targeted`，三个 target 零错误零警告一次通过，说明既有的队列
  约束与主队列回投是自洽的。

**对计划的偏离**：原计划是整块搬运 `MediaSaveOrchestrator`。实施时改为提取纯状态机，
因为编排逻辑与恢复仓库、保存协调器、相册服务、视频协调器及 6 处界面发布深度耦合，整块
搬运需要引入大量回调，既不减少复杂度，又要改动项目里不变量最密集的代码。提取判断逻辑用
不到十分之一的风险拿到了绝大部分测试收益。

## 三、附加交付

### 真机安装脚本

个人开发签名约 7 天到期，此前续期要手敲一串带 Team ID、UDID 和设备标识的命令。
`scripts/install-to-device.sh` 一条命令完成选 Xcode、找设备、签名、覆盖安装、启动。

四项自动探测，每一项都有不能写死的理由：

| 项 | 方式 | 原因 |
| --- | --- | --- |
| Xcode | 取 iOS SDK 版本最高的 | 系统升级后写死路径会失效 |
| 设备 | `reality == "physical"` | 模拟器同样报告 `platform: iOS`，只按平台过滤会选错 |
| Bundle ID | 反查设备已装的同名应用 | 按用户名拼前缀会猜错，会装成第二个应用而不是覆盖 |
| Team ID | 读本机描述文件 | 不能进仓库 |

后两条是**实跑时暴露的**：第一次运行选中了模拟器，且生成的 Bundle ID 与设备上实际的
不一致。个人值保存在 gitignore 的 `scripts/.device-config`。

### 应用图标

原图标是写实的双镜头位图：同心圆细节在 40×40 下糊成一团，深色镜头压在深蓝背景上对比
不足，且图形是通用的「相机镜头」，没有表达本应用的特征。

新图标为粗描边光圈环加右下角画中画角标，角标位置与应用默认的画中画位置一致。角标四周
先开一圈槽再绘制，让光圈从背后穿过时留出干净间隙——没有这道间隙，两个白色形状在小尺寸
下会粘连成一团。

改为由 `DesignAssets/make-app-icon.swift` 生成而非提交不可复现的位图，输出常规、深色、
单色三份 1024，资源目录改用单尺寸格式由 Xcode 自动派生全部尺寸。

设计过程中否决了三版，原因均已记录：画中画压出画框边界会读成挂锁；镜头环与画中画在
3:4 画框内必然贴合，形成钥匙孔；实心卡片加两处挖空虽清晰，但白色体量过大像家电。

配色最终选定浅天蓝配白（`#8CC1FF → #3E78E8`）。**已如实记录取舍**：白色配浅蓝的对比度
低于深蓝底，小尺寸下观感偏柔；若后续觉得发虚，加深渐变末端即可，图形无需改动。

只赶上 t=0 那一次。最终改为注入工作队列并同步排空，连跑三轮验证稳定。

## 五、经验与约束

以下几条已写入 `CLAUDE.md` 的不变量清单，避免重蹈：

1. **照片尺寸设置顺序**：`maxPhotoDimensions` 必须在连接建立之后设置，否则抛 NSException
   直接杀进程，且 Swift 侧捕获不到。
2. **坐标系差异**：预览与照片走 UIKit 坐标，视频合成走 CoreImage，y 轴方向相反。
3. **队列职责**：视频帧回调与合成必须留在独立队列，不能挪回 sessionQueue。
4. **纯状态提取**：新的判断逻辑应放进 `RecentMediaState` / `CameraNoticeCenter`，而不是
   内联回 Controller。
5. **格式缓存**：已验收组合按设备与模式缓存，全部候选失败时清除该键。
6. **Fake Camera 的边界**：它不走真实 AVCapture 路径，配置顺序、成本、镜头组合、压力回调、
   麦克风音画、相册最终文件方向都测不出来，必须装机。
