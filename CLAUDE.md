# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Native SwiftUI dual-camera app for iPhones that support `AVCaptureMultiCamSession` (target device: iPhone 16 Pro). It captures front+back photos concurrently, composes them into one image per a shared layout engine, and separately supports front+back picture-in-picture video recording. Repo docs and commit messages are in Chinese; code identifiers and comments are in English.

Two-way photo/video capture is "near-synchronous" — the app pairs results by transaction/time proximity, but iOS provides no public guarantee of exact simultaneous exposure or frame-level hardware sync.

## Fake Camera Mode

Launching with `-fakeCamera` (see `MultiCamSessionController.isFakeCamera`, `FakeCameraFactory`) substitutes synthetic front/back source images instead of driving real `AVCaptureMultiCamSession` hardware. This is what `DualCameraUITests` runs under, and it's the only way to exercise capture/save/recording flows in the simulator. Related flags used by tests to simulate failure paths: `-fakePhotoSaveFailure`, `-fakeMediaSaveDelay`. Unit tests never touch real PhotoKit or `AVCaptureSession` (`PhotoLibraryService` is injected via a `PhotoLibraryClient` protocol; `CameraPreferences` injects `UserDefaults`). The project builds under `SWIFT_STRICT_CONCURRENCY: targeted` with zero warnings — keep it that way.

## Architecture

Full detail lives in `docs/architecture.md` (includes a data-flow diagram) — read it before making non-trivial changes to capture, save, or recovery logic. Summary:

```
SwiftUI Views → CameraViewModel (MainActor)
             → MultiCamSessionController (holds AVCaptureMultiCamSession)
                 → CameraLifecycleCoordinator   (idempotent start/stop decisions)
                 → CameraSessionConfigurator    (builds the MultiCam graph)
                     → CameraFormatSelector     (scores format candidates)
                     → PhotoCaptureCoordinator  → CaptureTransactionManager
                     → VideoCaptureCoordinator  → DualCameraVideoRecorder
                 → PhotoComposer                (composites final image)
                 → MediaSaveCoordinator         → PhotoLibraryService (PhotoKit)
                 → MediaRecoveryStore           (in-process photo retry / UserDefaults video paths)
```

Key invariants to preserve when touching this code:

- **Queues**: all session/connection/device-lock/capture-coordinator state changes happen on the serial queue `com.taoking.dualcamera.session`; photo compositing never runs on the main thread. Video frame callbacks and compositing run on their own serial queue `com.taoking.dualcamera.video-output` — never move them back onto the session queue, or per-frame rendering will block focus, zoom, device locking and stop-recording. Lifecycle calls from the session queue enter that queue with `sync`. JPEG encoding and PhotoKit save scheduling happen on a separate `com.taoking.dualcamera.media-save` queue so saves never block the session queue. `@Published` UI state is always delivered back on main.
- **Non-blocking save**: photo/video saves happen on a background queue and never stop the live `AVCaptureMultiCamSession` or force-open the media viewer. Live preview, focus, and the next capture are decoupled from the save queue.
- **Save identity**: `MediaSaveCoordinator` dedupes by task ID (photo UUID or normalized video URL); mutex for a given ID is held until the real PhotoKit callback returns — no local timeout-based release, to avoid racing an unretryable retry against an in-flight write.
- **Pure state extraction**: the hardest media invariants live in `RecentMediaState` (ordering, video keep/delete decisions, one-shot auto-retry) and `CameraNoticeCenter` (notice timing). Both are free of AVFoundation/PhotoKit/filesystem/UI so they are directly unit-tested — keep new decision logic there rather than inlining it back into the controller.
- **Monotonic ordering**: Controller assigns a monotonic sequence number to successfully-started videos and subsequent photos on the session queue; only results with a sequence not earlier than the current "most recent media" are allowed to replace the thumbnail. This stops a slow-finishing video from clobbering a newer photo.
- **Recovery caps**: `MediaRecoveryStore` strong-retains up to 5 unfinished photo save operations in-process; failed video paths are persisted to `UserDefaults` (normalized `.mov` paths) so a new Controller instance can rediscover and retry them. Starting a new recording is blocked (with a `.retryMediaSaves` notice) if the union of failed+saving video files already numbers 5 or totals 1 GiB.
- **Notice priority**: `CameraNoticePolicy` prevents a lower-priority notice from clobbering an unresolved actionable one; each notice carries a unique ID and is only dismissed by consuming that exact ID, so a stale button can't clear a notice published after it.
- **Format/cost fallback**: format selection tries up to 6 candidate combinations at 30fps, then up to 6 at 24fps (never unbounded retry), accepting only when both `hardwareCost` and `systemPressureCost` are `<= 1` after committing the full session graph. The accepted combination is cached per (back device, front device, mode) and retried first on the next rebuild — mode switches, lens switches and quality changes all rebuild, and re-running the full search each time is what makes the record button feel slow. The cache is cleared for that key if every candidate fails. Photo and video score formats differently — photo ranks by the format's largest requestable photo dimensions (binning penalised), video targets 1920x1080 (binning rewarded, since the composite canvas is capped anyway). In both modes the 30fps preference outweighs any resolution difference.
- **Photo resolution**: `AVCapturePhotoOutput.maxPhotoDimensions` and each request's `AVCapturePhotoSettings.maxPhotoDimensions` must both be set explicitly, and only *after* the connection is added — this MultiCam graph uses `addOutputWithNoConnections`, so before that the output has no video source device and the setter throws `NSInvalidArgumentException`, which Swift cannot catch and which kills the process. Fake Camera Mode does not exercise the real AVCapture path, so changes to AVFoundation configuration ordering must be verified on device.
- **Coordinate systems**: `DualCameraLayoutEngine` emits UIKit rects (top-left origin, y down). Photo compositing and preview use them directly; video compositing runs through CoreImage (bottom-left origin, y up) and must convert via `coreImageRect(from:canvasHeight:)`, or the PIP lands in the vertically-opposite corner.
- **Video finalize semantics**: stopping video immediately switches back to photo preview and restarts the viewfinder session (not gated on the save completing); only after `AVAssetWriter.finishWriting` completes does the file get enqueued for PhotoKit save. Video URLs have explicit saving/saved/failed state — this exists specifically to avoid delete-vs-replace races between a save completing and the thumbnail being replaced by newer media.
